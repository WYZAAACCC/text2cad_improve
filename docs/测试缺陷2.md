# 总结判断

这份 v3.0 比上一版进步很大：`Retrieve()` 直接返回真实 `TDocStd_Document`，确实排除了“`Open(path, Handle<Document>&)` 没有把新句柄回写给 Python”这一层问题。报告对同进程 `AlreadyRetrieved`、`FindAttribute` 的 Restore 壳对象、`TDF_Tool.Label_s` 崩溃等结论也基本正确。([GitHub][1])

但是，报告最核心的结论——

> “普通 `TDataStd_*` 和 `TNaming_*` 在 XBF 持久化层中普遍丢失”

**仍然没有被这些测试证明。**

新版测试中还藏着一个更基础的标签使用错误：

```python
app.InitDocument(doc)
lbl = doc.Main().NewChild()
```

这里的 `lbl` 并不是新建的用户标签，而极有可能就是 XCAF 的系统保留标签：

```text
0:1:1  Shapes
```

因此，测试真正证明的只是：

> 在 XCAF 的保留 `Shapes` 工具标签上附加的额外用户属性，重开后没有被观察到。

这和“所有普通 OCAF 标签上的用户属性都无法持久化”是两件完全不同的事。

---

# 一、v3.0 中最关键的新测试是否有效

## `Retrieve()` 测试：读取方式有效，标签选择无效

报告的测试 7 正确地改用了：

```python
doc = app.Retrieve(folder, filename)
```

返回的是直接的文档对象，不再依赖输出 Handle。Reader 得到：

```text
RETRIEVE_OK type=TDocStd_Document
NB=2
ATTRS=["TDataStd_Name", "XCAFDoc_ShapeTool"]
```

所以可以确认：

* 读取到的不是调用前预创建的空文档；
* `Open()` 输出句柄问题已经被绕过；
* 当前读取到的标签确实只有两个属性。([GitHub][1])

但 Writer 是：

```python
app.InitDocument(doc)
lbl_w = doc.Main().NewChild()
```

Reader 是：

```python
c = doc.Main().FindChild(1, False)
```

问题恰恰就在这里。

---

# 二、`Main().NewChild()` 实际返回了 XCAF 的 Shapes 标签

## 1. XCAF 初始化已经占用了子标签 1～10

`XCAFDoc_DocumentTool` 在初始化文档时，会在文档主标签下建立固定服务标签：

| Tag | XCAF 用途         |
| --: | --------------- |
|   1 | Shapes          |
|   2 | Colors          |
|   3 | Layers          |
|   4 | D&GTs           |
|   5 | Materials       |
|   7 | Views           |
|   8 | Clipping Planes |
|   9 | Notes           |
|  10 | VisMaterials    |

其中 Shapes 的源码就是：

```cpp
TDF_Label L = DocLabel(acces).FindChild(1, Standard_True);
TDataStd_Name::Set(L, "Shapes");
```

随后 `XCAFDoc_ShapeTool` 被安装到该标签。([GitHub][2])

这与报告 Writer 的保存前输出完全一致：

```text
['TDataStd_Name', 'XCAFDoc_ShapeTool', 'TDataStd_Integer']
```

一个真正新建的普通用户标签，不会天然自带：

```text
TDataStd_Name("Shapes")
XCAFDoc_ShapeTool
```

这已经直接表明 `lbl_w` 就是 Shapes 标签。

---

## 2. 为什么 `NewChild()` 会撞到已经存在的 Tag 1

`TDF_Label.NewChild()` 底层使用 `TDF_TagSource::NewChild()`。

其行为是：

```cpp
if 标签上没有 TDF_TagSource:
    创建 TDF_TagSource，初始 myTag = 0

newTag = ++myTag;       // 第一次得到 1
return label.FindChild(newTag, true);
```

它并不会扫描当前标签下已经由 `FindChild(1)`、`FindChild(2)` 创建的现有子节点，也不会自动把计数器推进到最大已有 Tag。([GitHub][3])

所以执行顺序实际是：

```text
app.InitDocument(doc)
    ↓
XCAF 用 FindChild 创建 1、2、3、4、5、7、8、9、10

doc.Main().NewChild()
    ↓
Main 上原本没有 TDF_TagSource
    ↓
TagSource 从 0 开始
    ↓
第一次 NewTag() 返回 1
    ↓
FindChild(1, true)
    ↓
返回已经存在的 Shapes 标签
```

第二次调用 `Main().NewChild()`，会返回已有的 Colors 标签；第三次会返回 Layers 标签。

因此报告中很多测试实际上是在 XCAF 的系统服务树上写测试数据。

---

# 三、这能完整解释哪些实验现象

## 1. 为什么保存前天然有 Name 和 ShapeTool

因为测试标签不是用户标签，而是：

```text
0:1:1 Shapes
```

它本来就拥有：

```text
TDataStd_Name
XCAFDoc_ShapeTool
```

## 2. 为什么 Reader 固定 `FindChild(1)` 总能找到内容

报告把：

```text
Main().HasChild() == True
FindChild(1).IsNull() == False
```

视为“用户标签树被正确重建”的证据。

其实这只能证明 XCAF 的 Shapes 服务标签存在。任何正常 XCAF 文档初始化后都会有它。它不能证明 Writer 创建的“用户测试标签”被持久化，因为 Writer 压根没有创建独立用户标签。

## 3. 为什么 Name 能保留，而 Integer、Real 等消失

Reader 看到的 `TDataStd_Name` 可能只是 XCAF 在初始化/读取文档结构时重新确保存在的 `"Shapes"` 名称，并不是测试中设置的业务名称。

报告测试 2 执行：

```python
TDataStd_Name.Set_s(lbl, "TestLabel")
```

但这里是在给 Shapes 标签改名。重开后出现 `TDataStd_Name` 这个类型，不能证明 `"TestLabel"` 的值被保存；应当同时输出 Name 的实际字符串值。

若重开后值重新变成 `"Shapes"`，那更能证明看到的是 XCAF 服务结构恢复，而不是业务属性成功往返。

## 4. 文件体积增加也被 `TDF_TagSource` 污染

第一次调用：

```python
doc.Main().NewChild()
```

不仅获取了 Tag 1，还会在 Main 标签上添加一个 `TDF_TagSource` 属性。

因此“加一个 Integer 后文件增加若干字节”不能全部归因于 Integer；部分增量很可能来自刚刚创建的 TagSource，以及其他被修改的 XCAF 服务属性。文件大小测试只能算弱旁证。

# 四、对报告各结论的重新评级

| v3.0 结论                                 | 核查结果                 |
| --------------------------------------- | -------------------- |
| 同进程 `Open` 返回 `AlreadyRetrieved`，原测试无效  | 正确                   |
| `FindAttribute` 返回无 Label 的 Restore 壳对象 | 正确                   |
| `TDF_Tool.Label_s` 有输出参数崩溃风险            | 实验支持                 |
| `Retrieve()` 能返回真正读取的文档                 | 正确                   |
| `Open` 输出 Handle 是当前属性丢失的根因             | 已排除                  |
| `NbAttributes()` 自身不受 Restore 壳影响       | 正确                   |
| Reader 看到的 `FindChild(1)` 是用户测试标签       | 错误，它是 XCAF Shapes 标签 |
| `3→2` 证明普通标签属性普遍丢失                      | 不成立                  |
| `AddAttribute` 与 `Set_s` 都无法持久化         | 尚未证明                 |
| `NewDocument` 与手动 `InitDocument` 等价     | 尚未证明                 |
| BinMDataStd/BinMNaming 持久化驱动损坏          | 尚无证据                 |
| 当前 OCP 7.8.1 无法实现原生持久化                  | 结论过早                 |
| 必须升级 OCP 或重写驱动                          | 结论过早                 |

报告的测试 6 和测试 7确实证明：

```text
Shapes 标签保存前 3 个属性
重开后观察到 2 个属性
```

但它没有证明：

```text
任意应用自有标签上的 Integer 都会丢失
```

报告将局部现象推广成全局持久化故障，这一步目前不成立。([GitHub][1])

# 五、报告中 `NewDocument` 测试仍然无效

测试 3 使用：

```python
doc1 = TDocStd_Document(...)
app1.NewDocument("BinXCAF", doc1)
```

随后发现 `doc1` 没有 XCAF 初始化属性，仅有手工加入的 Integer。([GitHub][1])

这仍然高度说明：

```text
NewDocument(format, Handle<Document>&)
```

的输出 Handle 没有可靠回写到 Python 变量。

`Retrieve()` 只修复了 Reader，它并没有让 Writer 端的 `NewDocument` 输出参数突然变正常。

因此不能根据这组测试得出：

> `NewDocument` 和手动构造 Document + `InitDocument` 对持久化没有区别。

要验证真正的 `NewDocument`，仍需要：

* 返回值式 C++ 包装；
* 或 C++ Writer；
* 或在 OCP fork 中增加返回文档对象的方法。

# 六、应该立刻执行的决定性测试

不需要先改驱动，也不需要先升级 OCP。第一步只改标签。

## 测试 A：应用专用标签往返

Writer：

```python
from OCP.XCAFApp import XCAFApp_Application
from OCP.BinXCAFDrivers import BinXCAFDrivers
from OCP.TCollection import TCollection_ExtendedString
from OCP.TDocStd import TDocStd_Document
from OCP.TDataStd import TDataStd_Integer, TDataStd_Name
from OCP.TDF import TDF_Tool

DESIGN_ROOT_TAG = 100
TEST_LABEL_TAG = 1

app = XCAFApp_Application.GetApplication_s()
BinXCAFDrivers.DefineFormat_s(app)

doc = TDocStd_Document(TCollection_ExtendedString("BinXCAF"))
app.InitDocument(doc)

doc.NewCommand()

# 不能用 Main().NewChild()
design_root = doc.Main().FindChild(DESIGN_ROOT_TAG, True)
test_label = design_root.FindChild(TEST_LABEL_TAG, True)

TDataStd_Name.Set_s(
    design_root,
    TCollection_ExtendedString("Text2CADDesignRoot"),
)

integer_attr = TDataStd_Integer()

# 建议先挂接，再 Set，顺便排除脏标记时序问题
test_label.AddAttribute(integer_attr)
integer_attr.Set(42)

doc.CommitCommand()

print("design tag:", design_root.Tag())  # 应为 100
print("test tag:", test_label.Tag())     # 应为 1
print("attrs:", test_label.NbAttributes())

status = app.SaveAs(
    doc,
    TCollection_ExtendedString(str(output_path)),
)
```

Reader：

```python
app = XCAFApp_Application.GetApplication_s()
BinXCAFDrivers.DefineFormat_s(app)

doc = app.Retrieve(folder, filename)

design_root = doc.Main().FindChild(100, False)
assert not design_root.IsNull()

test_label = design_root.FindChild(1, False)
assert not test_label.IsNull()

print("NB:", test_label.NbAttributes())
```

必须同时检查：

```text
0:1:1     XCAF Shapes
0:1:100   Text2CAD DesignRoot
0:1:100:1 Test Label
```

而不是只打印 `FindChild(1)`。

## 测试 B：保留标签与普通标签对照

同一个文档中写两份相同数据：

```text
A：Main().FindChild(1)       XCAF Shapes 保留标签
B：Main().FindChild(100)     应用自有标签
```

分别加：

* Integer；
* Real；
* AsciiString；
* Name。

重开后会出现三种可能：

### 结果 1

```text
Shapes 上丢失
Tag 100 上全部保留
```

结论：

> XBF 持久化正常，旧测试只是污染 XCAF 工具标签。

这是我目前认为概率最高的结果。

### 结果 2

```text
Shapes 和 Tag 100 都丢失
```

结论：

> 确实存在更底层的保存、文档创建或驱动问题，需要进入 C++ 四象限测试。

### 结果 3

```text
attach → Set 保留
Set → AddAttribute 丢失
```

结论：

> 属性修改时序或 OCAF transaction/Backup 语义存在问题，不是驱动缺失。

# 七、必须增加全标签树转储

现在报告始终假定“我要的标签就是 Child 1”。下一版测试必须在 Writer 和 Reader 都递归输出：

```text
Entry
Tag
Depth
Name 的实际值
所有 Attribute 动态类型
NbAttributes
```

使用：

```python
TDF_Tool.Entry_s(label, ascii_string)
```

和：

```python
TDF_ChildIterator
TDF_AttributeIterator
```

不要使用会崩溃的反向 API：

```python
TDF_Tool.Label_s(...)
```

建议预期输出类似：

```text
0:1
  attributes:
    XCAFDoc_DocumentTool
    TDF_TagSource

0:1:1
  name: Shapes
  attributes:
    TDataStd_Name
    XCAFDoc_ShapeTool

0:1:100
  name: Text2CADDesignRoot

0:1:100:1
  attributes:
    TDataStd_Integer = 42
```

这样一眼就能分清“属性丢了”还是“看错标签了”。

# 八、仓库正式代码也存在同一个致命错误

当前 `OcafDocumentSession` 初始化代码是：

```python
app.InitDocument(doc)
self._design_label = doc.Main().NewChild()  # DesignRoot (0:1:1)
```

也就是说，正式系统把：

```text
0:1:1 Shapes
```

错误地当成了：

```text
Text2CAD DesignRoot
```

而 `get_or_create_component_label()` 又继续在该标签下调用 `NewChild()`。([GitHub][4])

这会导致：

* Text2CAD 元数据写入 XCAF Shapes 工具树；
* 自定义 Feature 标签和 XCAF shape 子标签争抢 Tag；
* `TNaming_Builder`、Selector 和 ShapeTool 共享或污染标签；
* 重开时 XCAF 初始化逻辑可能重建服务属性；
* 几何、组件、选择集和 XCAF shape registry 混在一起；
* 所谓稳定 Tag 从一开始就不稳定。

这不是小问题，而是当前 OCAF 实现的 P0 级错误。

# 九、正式代码应怎样改

建议固定使用远离 XCAF 保留区的 Tag：

```python
DESIGN_ROOT_TAG = 100

SCHEMA_TAG = 1
COMPONENTS_TAG = 2
SELECTIONS_TAG = 3
REVISIONS_TAG = 4
CAE_BINDINGS_TAG = 5
ID_INDEX_TAG = 6
```

初始化：

```python
self._design_label = doc.Main().FindChild(
    DESIGN_ROOT_TAG,
    True,
)

self._schema_label = self._design_label.FindChild(
    SCHEMA_TAG,
    True,
)

self._components_label = self._design_label.FindChild(
    COMPONENTS_TAG,
    True,
)
```

重开：

```python
self._design_label = doc.Main().FindChild(
    DESIGN_ROOT_TAG,
    False,
)

if self._design_label.IsNull():
    raise OcafSchemaError(
        "Missing Text2CAD DesignRoot at tag 100"
    )
```

标签树可以固定为：

```text
0:1
├── 1   XCAF Shapes
├── 2   XCAF Colors
├── 3   XCAF Layers
├── ...
├── 10  XCAF VisMaterials
└── 100 Text2CAD DesignRoot
    ├── 1 Schema
    ├── 2 Components
    ├── 3 Selections
    ├── 4 Revisions
    ├── 5 CAE Bindings
    └── 6 ID Index
```

在 Main 下禁止：

```python
doc.Main().NewChild()
```

在需要稳定身份的任何位置也尽量禁止无约束 `NewChild()`，统一用持久化的显式 Tag 映射。

# 十、修正标签后，下一步怎样定位剩余问题

## 第一层：纯 Python，普通标签

依次测试：

```text
TDataStd_Integer
TDataStd_Real
TDataStd_AsciiString
TDataStd_Name
TDataStd_Reference
TNaming_Builder.Generated
TNaming_Selector.Select
```

全部写在 `0:1:100:*`。

## 第二层：二进制与 XML 对照

同一个测试文档分别保存：

```text
BinXCAF
XmlXCAF
```

若 XML 保留而二进制丢失，才集中调查 BinM 驱动；若两者都丢，优先调查标签、文档创建和 transaction。

## 第三层：C++/Python 四象限

| Writer | Reader |
| ------ | ------ |
| C++    | C++    |
| Python | C++    |
| C++    | Python |
| Python | Python |

所有测试都必须写在显式 Tag 100，而不是 XCAF 保留标签。

## 第四层：真正的 NewDocument

增加一个最小 C++ 返回值包装：

```cpp
Handle(TDocStd_Document) NewXcafDocument()
{
    Handle(TDocStd_Document) doc;
    auto app = XCAFApp_Application::GetApplication();
    BinXCAFDrivers::DefineFormat(app);
    app->NewDocument("BinXCAF", doc);
    return doc;
}
```

这可以消除 Writer 端 `NewDocument(..., Handle<Document>&)` 输出绑定的不确定性。

## 第五层：打开 OCCT native 日志

只有出现明确的：

```text
unknown attribute type
driver not found
failure reading attribute
```

才有证据将问题归因于 BinMDataStd/BinMNaming 驱动。

# 十一、TNaming 真正落地仍需修复的其他问题

即便新测试证明 XBF 能正常保存 TNaming，仓库还不能立即获得“原生持久拓扑命名”，因为应用层仍有以下问题：

1. History 捕获后只保存数量和几何 evidence，丢弃真实 old/new `TopoDS_Shape`；
2. `Modify` 被 writer 写成 `Generated`；
3. `Delete` 使用最终 result shape，而不是被删除的旧 shape；
4. Selection 和业务属性没有完全隔离标签；
5. 创建与重开使用不同 DesignRoot；
6. `FindAttribute` 仍只能得到 Restore 壳，应通过 Selector、AttributeIterator 或安全 C++ 返回值接口访问真实 Handle；
7. OCAF 保存后尚缺独立进程重开验证与原子发布闭环。

所以标签冲突是当前最前面的阻塞点，但不是最后一块拼图。

---

# 最终修正结论

v3.0 可以保留的结论是：

> `Retrieve()` 返回真实文档；`Open` 输出句柄不是当前 Reader 的问题；`FindAttribute` 和 `TDF_Tool.Label_s` 的 OCP 绑定确实不安全；在 XCAF 的 Shapes 保留标签上附加的普通属性，当前测试中没有在重开后观察到。

v3.0 暂时不能保留的结论是：

> 普通用户标签上的 `TDataStd_*` 和 `TNaming_*` 在 XBF 中普遍无法持久化，或者 OCP 7.8.1 的 BinMDataStd/BinMNaming 驱动已经被证明损坏。

当前最优先的动作不是升级版本、重写 BinMNaming 或建立新的拓扑数据库，而是：

```text
停止使用 Main().NewChild()
        ↓
在 Tag 100 创建独立 DesignRoot
        ↓
对照测试 Shapes 标签与普通标签
        ↓
递归转储完整 Label 树
        ↓
再判断属性是否真的丢失
```

这次有点像抓“幽灵属性丢失”，结果先发现测试台搭在 XCAF 的机房配电柜上了。先把实验搬到自己的房间，再判断电到底去哪儿了。
