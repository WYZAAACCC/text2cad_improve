我核对的是 main 分支最新提交 `d30e2c314433e0e6d8acd0b9e2f7d3358b9ed49b` 中的 v3.0 最终版。这个版本新增了 Test 9：`START_TYPES`、ASCII 路径、BinXCAF/XmlXCAF 对照以及 Tag 100 用户标签测试。([GitHub][1])

# 总体判断

这次测试取得了真正的突破，但报告的最终结论需要收紧为：

> **OCP 7.8.1.1 下，普通 OCAF 标签和 `TDataStd_*` 属性的 BinXCAF/XmlXCAF 跨进程持久化是可用的；此前大量失败高度可能由错误的路径字符串构造、Session 复用和 XCAF 保留标签冲突共同造成。**

但目前还不能严谨地写成：

> “OCAF/TNaming 原生持久化完全正常，T0～T12 都可以通过。”

原因是新 Test 9 主要证明了普通 `TDataStd` 属性持久化，**还没有完成真正的 TNaming 跨 Revision 拓扑跟踪测试**。

# 一、新测试中已经正确证明的内容

## 1. 标准属性驱动确实已经注册并参与保存

XBF 的 `START_TYPES` 中出现了：

* `TDataStd_Name`
* `TDataStd_Integer`
* `TDataStd_Real`
* `TDataStd_AsciiString`
* `XCAFDoc_ShapeTool`
* `TDataStd_TreeNode`

这足以排除先前的主要猜测：

> `BinMDataStd` 没注册，或者 `GetDriver(attribute.DynamicType())` 完全匹配不到驱动。

至少对这些测试属性，Storage Driver 已经识别到了类型。

不过，`START_TYPES` 只能证明类型被驱动表识别并写入类型表，单独看它不能证明每个 Attribute payload 都正确；后续 ASCII 路径下的实际往返结果才完成了这一证据链。

## 2. ASCII 路径下，普通 OCAF 属性确实可以跨进程恢复

新版报告在 ASCII 路径下观察到：

```text
Tag 100: FOUND
Tag 100:1: FOUND
TDataStd_Integer(42): FOUND
TDataStd_Name: FOUND
```

而且 BinXCAF 与 XmlXCAF 都可以恢复 Tag 100 用户树。这说明：

* 用户标签并不需要放在 XCAF 系统工具树里；
* 普通 `TDataStd` 属性可以被保存；
* OCP 7.8.1.1 并不是天然无法使用 OCAF 持久化；
* 不需要重写 `BinMDataStd` 驱动。

## 3. `Main().NewChild()` 冲突问题已经被实验证实

报告打印出：

```text
NewChild #1 → Tag 1 / Shapes
NewChild #2 → Tag 2 / Colors
```

这和仓库当前实现完全对应：`document.py` 仍然把 `doc.Main().NewChild()` 当作 DesignRoot，后续组件和 feature 同样依赖 `NewChild()`。这会把 Text2CAD 数据写入 XCAF 系统标签，并造成标签身份不稳定。

这项结论是确定的，而且当前正式代码尚未修复。

## 4. `FindAttribute` 与 `TDF_Tool.Label_s` 仍然不能安全使用

新版没有改变这两个判断：

* `FindAttribute` 返回的对象可能只是通过 `Restore()` 复制内容的壳对象，不保留原 Label；
* 属性不存在时，包装层缺乏 null guard，可能直接崩溃；
* `TDF_Tool.Label_s` 的输出 Label 引用也存在原生崩溃风险。

因此当前系统仍需通过：

* `TDF_AttributeIterator`
* `TNaming_Selector.NamedShape()`
* 明确的 `FindChild(tag, create)`
* 或安全 C++ 返回值接口

来访问对象。

# 二、报告中仍然存在的几个推断问题

## 1. “中文路径是唯一且已经完全确认的根因”证据还差一个严格对照

目前报告比较的是：

* 旧测试：`tempfile.mkdtemp()` 路径；
* 新测试：固定 ASCII 路径；
* 同时还修改了标签、Reader、遍历方式以及测试脚本。

因此新结果**强烈支持路径编码是重要根因**，但尚不是严格的单变量实验。

真正决定性的测试必须是：

```text
完全相同的 Writer
完全相同的 Reader
完全相同的标签和属性
唯一变化：目录名是否含中文
```

报告目前没有完整展示这样的 A/B 原始输出，因此“确认路径编码为唯一根因”略微过度。

建议结论改为：

> 非 ASCII 路径与失败具有稳定相关性，并与当前 `TCollection_ExtendedString` 构造方式的编码语义相符；需通过完全相同脚本的 Unicode/ASCII 单变量实验最终确认。

## 2. 问题不是 `TCollection_ExtendedString` 本身不能处理中文

报告写道：

> `TCollection_ExtendedString` 无法处理非 ASCII 路径。

这不准确。

OCCT 7.8 的 `TCollection_ExtendedString` 本身就是 UTF-16 字符串，并提供：

```cpp
TCollection_ExtendedString(
    const char* string,
    bool isMultiByte = false
)
```

当 `isMultiByte=true` 时，输入才按 UTF-8 解码；默认值却是 `false`。当前仓库使用：

```python
TCollection_ExtendedString(str(path))
```

没有传第二个参数，因此 Python `str` 经绑定转成 UTF-8 字节后，很可能被逐字节复制成错误的 UTF-16 字符。([Open CASCADE Technology][2])

所以真正的问题更可能是：

> **OCP/Python 调用了 `TCollection_ExtendedString(const char*, false)` 这个错误重载语义。**

不是：

> OCCT 不支持 Unicode 路径。

OCCT 官方资料明确说明，`TCollection_ExtendedString` 用于 Unicode，UTF-8 输入需要正确转换。([Open CASCADE Technology][3])

## 3. Test B 中“子标签仍丢失”很可能只是遍历方式错误

报告在同一个 ASCII 路径测试中先得到：

```text
Tag 100: FOUND
Tag 100:1: NOT in children
```

紧接着另一个同样使用 ASCII 路径的测试又得到：

```text
Tag 100:1: FOUND
Integer(42): FOUND
```

这两组结果本身矛盾。

最可能的解释是 `TDF_ChildIterator` 的使用方式。

OCCT 中：

```cpp
TDF_ChildIterator(label, allLevels=false)
```

默认只遍历第一层。因此从 Main 开始遍历时能看到直接子标签 `0:1:100`，但看不到第二层的 `0:1:100:1`；这不能证明子标签丢失。([Open CASCADE Technology][4])

正确检查应为：

```python
child = design_root.FindChild(1, False)
```

或者：

```python
TDF_ChildIterator(main, True)
```

所以报告中所谓“XCAF 属性依赖测试解决了子标签丢失”，大概率不是属性依赖，而是前一测试的遍历器没有递归。

## 4. “全部用户属性均验证通过”展示的证据还不完整

最终结论声称验证了：

* Integer
* Real
* AsciiString
* Name

但 Test C 展示的原始输出只明确列出了：

* Integer；
* Name。

Test B 中虽然 Writer 写入了 Real 和 AsciiString，但 Reader 输出又声称子标签没找到。

因此最好增加一份单一、无歧义的最终结果：

```text
0:1:100
  TDataStd_Name = Text2CAD DesignRoot
0:1:100:1
  TDataStd_Name = Test Feature
  TDataStd_Integer = 42
  TDataStd_Real = 3.14
  TDataStd_AsciiString = hello
```

Writer 和独立 Reader 都输出实际值，而不只是类型名。

## 5. `Retrieve()` 没有证明 `Open()` 输出句柄绑定正常

报告把：

> “Open 输出 Handle 未回写”

标成被 `Retrieve()` 证伪。

严格说不对。

`Retrieve()` 绕过了 `Open(path, Handle<Document>&)`，所以它只能证明：

> 属性丢失不是 Retrieve 路径中的 Document Handle 问题。

它不能证明：

> `Open()` 的输出 Handle 在 OCP 中能够可靠回写。

仓库当前的 `open()` 仍然预创建文档、调用 `InitDocument()`，随后调用 `app.Open(..., doc)`，而且完全不检查 `PCDM_ReaderStatus`。

生产代码应直接改用已经验证过的 `Retrieve()`，不要再围着 `Open` 的输出参数打转。

# 三、最重要的限制：TNaming 仍未被最终验证

报告最终写道：

> OCAF/TNaming 原生持久化完全正常。

但 Test 9 的实际结果主要覆盖的是：

```text
TDataStd_Integer
TDataStd_Real
TDataStd_AsciiString
TDataStd_Name
```

没有展示下面这些对象在 ASCII 路径下的完整跨进程往返：

* `TNaming_NamedShape`
* `TNaming_Naming`
* `TNaming_Selector`
* `TNaming_Selector.Solve()`
* `TNaming_Tool.CurrentShape()`
* Generated/Modify/Delete 历史。



所以当前可以确认的是：

> **OCAF 基础持久化已经打通。**

尚不能确认的是：

> **Text2CAD 所需的原生持久拓扑命名闭环已经打通。**

尤其仓库当前的 `writer.py` 仍存在明确错误：

```python
DELETED  → Delete(batch.result_shape)
MODIFIED → Generated(batch.result_shape)
GENERATED → Generated(batch.result_shape)
```

而 `models.py` 明确不保存每条关系真实的 old/new Shape，writer 根本没有足够信息调用正确的 `Generated(old,new)`、`Modify(old,new)` 和 `Delete(old)`。

因此 Test 9 解决的是“文档能不能保存”，还没有解决“拓扑历史是否正确”。

# 四、路径问题的正确解决方式

## 方案 A：纯 Python 修正 UTF-8 构造

首先测试 OCP 是否暴露双参数构造：

```python
from pathlib import Path
from OCP.TCollection import TCollection_ExtendedString

def to_occt_path(path: Path) -> TCollection_ExtendedString:
    text = str(Path(path).resolve())
    return TCollection_ExtendedString(text, True)
```

第二个参数 `True` 表示把输入 `char*` 按 UTF-8 解释。其默认值是 `False`，这正是当前仓库的问题。([Open CASCADE Technology][2])

若该重载在 OCP 中不好用，可采用：

```python
from OCP.TCollection import (
    TCollection_AsciiString,
    TCollection_ExtendedString,
)

def to_occt_path(path: Path) -> TCollection_ExtendedString:
    utf8 = TCollection_AsciiString(str(Path(path).resolve()))
    return TCollection_ExtendedString(utf8, True)
```

这应当通过专门测试确认后再投入生产。

## 方案 B：C++ 安全路径桥接

长期最稳的实现是增加一个很小的 C++ 接口：

```cpp
TCollection_ExtendedString ToExtendedPath(
    const std::string& utf8Path)
{
    return TCollection_ExtendedString(
        utf8Path.c_str(),
        Standard_True);
}
```

Windows 下还可以直接从 `wchar_t*` 构建 `TCollection_ExtendedString`，避免中间 UTF-8 转换。OCCT 本身支持 wide-character/UTF-16 构造。([Open CASCADE Technology][2])

## 方案 C：ASCII 工作区作为兜底

即便完成 Unicode 修复，也建议几何工作进程使用统一 ASCII staging 目录：

```text
C:\text2cad_work\<job_uuid>\
```

完成 Save、Retrieve 和完整自检后，再由 Python 文件系统将合格文件复制或原子移动到用户指定目录。

但这应是**兼容性兜底**，不应成为“中文路径永久不支持”的架构限制。

# 五、仓库需要立刻修改的代码

## 1. 修复 `document.py`

当前代码的四个 P0 问题是：

* `Main().NewChild()` 错当 DesignRoot；
* 默认路径构造没有 UTF-8 标志；
* `open()` 使用不安全的输出 Handle API；
* 重开后把 `doc.Main()` 错当 DesignRoot。

建议骨架改为：

```python
DESIGN_ROOT_TAG = 100

def _occt_path(path: Path) -> TCollection_ExtendedString:
    return TCollection_ExtendedString(
        str(path.resolve()),
        True,
    )

def _create_design_root(doc):
    return doc.Main().FindChild(DESIGN_ROOT_TAG, True)

@classmethod
def open(cls, path: Path):
    app = XCAFApp_Application.GetApplication_s()
    BinXCAFDrivers.DefineFormat_s(app)

    p = Path(path).resolve()
    doc = app.Retrieve(
        _occt_path(p.parent),
        _occt_path(Path(p.name)),
        True,
    )

    root = doc.Main().FindChild(DESIGN_ROOT_TAG, False)
    if root.IsNull():
        raise OcafSchemaError("Missing DesignRoot tag 100")
```

## 2. 修复稳定 Label

禁止所有这些调用：

```python
doc.Main().NewChild()
design_root.NewChild()
feature_label.NewChild()
```

改为：

```text
固定 Tag 树
+
持久化 ID→Tag 索引
+
冲突检测
```

例如：

```text
0:1:100      DesignRoot
  :1         Schema
  :2         Components
  :3         Selections
  :4         Revisions
  :5         CAEBindings
  :6         IDIndex
```

## 3. 重构拓扑 History 数据模型

`EvolutionRelation` 必须保存当前进程内的真实拓扑句柄：

```python
@dataclass
class LiveEvolutionRelation:
    kind: EvolutionKind
    old_shape: TopoDS_Shape | None
    new_shapes: tuple[TopoDS_Shape, ...]
```

审计 JSON 另设一个模型，不要用面积、质心、数量反向猜 Shape。

## 4. 修复 TNaming Writer

必须严格映射：

```python
PRIMITIVE:
    builder.Generated(new_shape)

GENERATED:
    builder.Generated(old_shape, new_shape)

MODIFIED:
    builder.Modify(old_shape, new_shape)

DELETED:
    builder.Delete(old_shape)
```

当前 writer 把 Modify 写成 Generated、把最终实体作为 Delete 参数，这种历史即使成功持久化，也无法提供正确拓扑身份。

# 最终结论

新版报告的核心突破是真的：

> **OCP 7.8.1.1 中普通 OCAF 标签和标准属性可以原生持久化，不需要升级 OCP，也不需要重写 BinMDataStd/BinMNaming 驱动。**

但需要修正三处表述：

1. 不是 `TCollection_ExtendedString` 天生不支持中文，而是当前 Python 调用没有启用 UTF-8 解码；
2. ASCII 路径是强证据，但仍应做只改变路径的严格 A/B 测试；
3. 当前只证明了基础 OCAF 持久化，尚未证明真正的 TNaming `Select→Save→Retrieve→Modify→Solve` 闭环。

最合理的实施顺序已经收敛为：

```text
修正 UTF-8 路径构造
→ 改用 Retrieve
→ 固定 Tag 100 DesignRoot
→ 去除全部 NewChild 身份分配
→ 保存真实 old/new Shape
→ 修复 TNaming Writer
→ 执行跨进程、跨 Revision 的 TNaming T0～T12
```

现在最大的好消息是：**底层持久化地基基本没塌。真正剩下的主战场，已经回到仓库自己的拓扑历史模型和 TNaming 写入语义上了。**
