# 核查结论

我阅读了 main 分支新提交 `0311cfc39685d61d033406ef953f846b246e6f41` 中更新后的报告。新版确实纠正了上一轮两个重要误判，但它的**核心结论仍然没有成立**：

> 新测试尚不能证明“XBF 跨进程后用户属性真的丢失”，更不能把根因归结为“pybind11 破坏了 BinMDataStd/BinMNaming 的反序列化 Paste”。

更可能的真实情况是：

```text
OCCT 在 C++ 内部已经成功读取 XBF
        ↓
Open() 将结果赋给 Handle(TDocStd_Document)& 输出参数
        ↓
OCP 没有把新的 Document Handle 可靠地回写到 Python 变量
        ↓
Reader 继续检查调用 Open 前预创建并 InitDocument 的空白文档
        ↓
空白文档恰好只有 Name、ShapeTool 等 XCAF 初始化属性
        ↓
被误判为“文件只恢复了框架属性，用户属性丢失”
```

而新版报告里的 `NewDocument` 测试，反而提供了这个判断的强证据。

---

# 一、新版报告中已经改对的部分

## 1. 同进程 `AlreadyRetrieved` 的修正是正确的

新版已经确认：

* `SaveAs()` 会把文档登记到 Application Session；
* 随后在同一 Application 中再次打开同一路径，会返回 `PCDM_RS_AlreadyRetrieved`；
* 此时 `Retrieve()` 根本不会执行；
* 原来检查的 `doc2` 是空文档。

这与 OCCT 7.8.1 的源码完全一致：`Open()` 只有在 `CanRetrieve()` 返回 `PCDM_RS_OK` 时才调用 `Retrieve()`；保存时也确实会把文档关联到 Application。([GitHub][1])

这一修正没有问题。

## 2. `FindAttribute` 的“Restore 壳对象”结论基本正确

OCP 7.8.1.1 没有直接绑定原生：

```cpp
FindAttribute(GUID, Handle<TDF_Attribute>&)
```

而是自定义成：

```cpp
Handle(TDF_Attribute) dummy_attr;
auto rv = self.FindAttribute(anID, dummy_attr);
anAttribute.Restore(dummy_attr);
return rv;
```

因此 Python 得到的并不是文档内部真正的 Attribute Handle，而是一个通过 `Restore()` 复制内容的独立壳对象，其 `Label()` 可能为空。([GitHub][2])

所以：

```text
FindAttribute 返回 True
≠
Python 已获得文档里的真实 TNaming_NamedShape Handle
```

这一判断是正确的。

## 3. BinMNaming 驱动无需 Python 手动注册

`BinXCAFDrivers::AttributeDrivers()` 会调用 `BinDrivers::AttributeDrivers()`；后者明确注册：

* `BinMDataStd`
* `BinMDataXtd`
* `BinMNaming`
* `BinMDocStd`
* `BinMFunction`

所以“需要在 Python 中手工逐一注册 BinMNaming 驱动”这一假设可以排除。([GitHub][3])

# 二、新版测试仍然存在的致命缺陷

## 1. 跨进程不等于拿到了正确的 Document

报告认为：

```text
独立 subprocess
+
PCDM_RS_OK
=
Python 中 doc 已经是磁盘读取的文档
```

这个等式不成立。

OCCT 的原生签名是：

```cpp
PCDM_ReaderStatus Open(
    const TCollection_ExtendedString& path,
    Handle(TDocStd_Document)& theDoc
);
```

`theDoc` 是**输出 Handle 引用**。OCCT 内部创建一个新的 `D`，读取文件，然后执行：

```cpp
theDoc = D;
```

它并不会把文件内容写进调用者事先构造的旧 `TDocStd_Document` 对象。([GitHub][4])

而新版所有 Reader 仍然采用：

```python
doc = TDocStd_Document("BinXCAF")
app.InitDocument(doc)
status = app.Open(path, doc)

# 接着检查原变量 doc
c = doc.Main().FindChild(1, False)
```

这没有验证 Python 变量 `doc` 是否真的被重新绑定到 C++ 输出的新 Handle。([GitHub][1])

`PCDM_RS_OK` 只能证明：

> OCCT 的 native `Retrieve()` 返回了成功状态。

它不能证明：

> pybind11 已把新 `Handle(TDocStd_Document)` 回写进 Python 变量。

---

## 2. `NewDocument` 测试实际上已经暴露了这个问题

报告的测试 3 得到：

```text
app.NewDocument() 后：
保存前只有 TDataStd_Integer
没有 TDataStd_Name / XCAFDoc_ShapeTool
```

报告把它当作“NewDocument 与 InitDocument 对持久化无影响”。

但根据 OCCT 源码，`TDocStd_Application::NewDocument()` 必定：

1. 新建一个 `TDocStd_Document`；
2. 调用虚函数 `InitDocument(D)`；
3. 将新 Handle 赋给输出参数。

对于 `XCAFApp_Application`，`InitDocument()` 必定调用：

```cpp
XCAFDoc_DocumentTool::Set(doc->Main());
```

也就是说，真正由 `NewDocument()` 返回的 XCAF 文档必然已经具有 XCAF 初始化结构。([GitHub][5])

现在 Python 中的 `doc1` 没有这些结构，最合理的解释不是“NewDocument 不初始化 XCAF”，而是：

> `app.NewDocument(format, doc1)` 在 C++ 中创建了另一个正确文档，但输出 Handle 没有回写进 Python 的 `doc1`；Python 继续操作的是调用前手工构造的旧对象。

这是整个报告里最接近“冒烟枪”的证据。

既然 `NewDocument` 的输出 Handle 已经表现出没有正确回写，那么同样使用：

```cpp
Handle(TDocStd_Document)&
```

的 `Open()` 当然也必须被视为不可信。

---

## 3. 为什么 Reader 中恰好只看到两个框架属性

Reader 在 `Open()` 前主动执行：

```python
app.InitDocument(doc)
```

而 XCAF 的 `InitDocument()` 会立即在这个旧空文档的 Main Label 上创建 `XCAFDoc_DocumentTool` 结构。([GitHub][6])

因此即使 `Open()` 的输出 Handle没有回写，旧 `doc` 也会呈现：

* `TDataStd_Name`
* `XCAFDoc_ShapeTool`
* XCAF 的若干固定子标签

这正好与报告所谓“重开后只保留框架属性”的结果吻合。

换句话说，这组现象可以被完整解释为：

```text
并没有读取到只有框架属性的文档
而是在读取调用 Open 前自行初始化的空白文档
```

报告公布的通用 Reader：

```python
def reader_subprocess(xbf_path, app_type="xcaf"):

    app = XCAFApp_Application.GetApplication_s()
    BinXCAFDrivers.DefineFormat_s(app)
```

`app_type` 参数根本没有被使用。也就是说，测试 A 虽然 Writer 使用：

但 Reader 仍使用：

```text
XCAFApp_Application
```

```python
if format_kind == "BinOcaf":

    app = XCAFApp_Application.GetApplication_s()

```

当然，即便修正应用类型，仍必须首先解决 `Open()` 输出 Handle 的问题。

# 五、`NbAttributes 3→2` 为什么不是“决定性证据”

报告声称 `NbAttributes()` 没有输出参数，因此排除了绑定干扰。

这个论证只排除了：

```text
NbAttributes 自己的返回值绑定错误
```

它没有排除：

```text
调用 NbAttributes 的 c 属于错误文档
```

当前 Reader 的对象链是：

```python
old_doc = TDocStd_Document(...)
app.InitDocument(old_doc)

app.Open(path, old_doc)   # 输出引用是否回写未验证

c = old_doc.Main().FindChild(...)
nb = c.NbAttributes()
```

所以 `NbAttributes()==2` 只能证明：

> Python 当前变量指向的 Label 上有两个属性。

它不能证明：

> XBF 中读取出的真实 Label 上只有两个属性。

因此新版报告中“决定性证据”的措辞必须撤销。([GitHub][1])

# 六、最终根因推断在技术机制上是错的

报告最终推测：

> `BinMDataStd_IntegerDriver::Paste()` 需要 `Handle(TDF_Attribute)&` 输出参数，而 pybind11 无法正确处理，所以反序列化失败。

这里有两个事实错误。

## 1. `Paste()` 并不使用 Attribute 输出参数

OCCT 7.8.1 的真实签名是：

```cpp
virtual Standard_Boolean Paste(
    const BinObjMgt_Persistent& source,
    const Handle(TDF_Attribute)& target,
    BinObjMgt_RRelocationTable& reloc
) const;
```

目标 Attribute 是 `const Handle<TDF_Attribute>&` 输入 Handle，不是需要重新赋值的输出 Handle。([GitHub][7])

`BinMDataStd_IntegerDriver::Paste()` 只是把 target 下转为 `TDataStd_Integer`，读取整数并调用 `Set()`。([GitHub][8])

## 2. 反序列化循环完全运行在 C++ 内部

OCCT 原生读取流程是：

```cpp
tAtt = aDriver->NewEmpty();
theLabel.AddAttribute(tAtt);
ok = aDriver->Paste(myPAtt, tAtt, myRelocTable);
```

这个调用链发生在 `BinLDrivers_DocumentRetrievalDriver::ReadSubTree()` 内部，全程是 C++ 虚函数调用。Python 和 pybind11 根本不参与每个 Attribute 的 `NewEmpty()` 和 `Paste()`。([GitHub][9])

pybind11 只介入最外层：

```text
Python → app.Open(...)
```

一旦进入 OCCT，持久化驱动之间是 native C++ 调用。

所以：

> “pybind11 无法把 Paste 创建的 Attribute 回传给文档”

在机制上不可能是当前故障原因。

真正可能受 pybind 影响的是：

> `Open()` 完成后，新的 Document Handle 能否回传给 Python。

# 七、二进制文件分析中的结论也需要修正

## 1. 文件大小增加不证明指定属性已正确写入

`+69 bytes` 或 `+8471 bytes` 说明文件内容发生了变化，支持“标签、属性或几何产生了额外记录”，但不能单独证明：

* 类型表正确；
* Attribute driver 被正确选择；
* Attribute payload 完整；
* 读取端必然能恢复。

它是旁证，不是排除序列化故障的决定性证据。

## 2. 搜不到默认 GUID 是正常现象

`BinMDataStd_IntegerDriver` 在写入时：

```cpp
target << integerValue;

if (attribute.ID() != TDataStd_Integer::GetID())
    target << attribute.ID();
```

也就是说，使用默认 GUID 的普通 `TDataStd_Integer` 根本不会把默认 GUID 写入 payload。([GitHub][8])

因此报告中：

> “二进制中找不到 TDataStd_Integer GUID，可能使用了非标准编码”

这个推断是不正确的。

XBF 通常通过文件头中的类型表和内部 TypeId 关联驱动，不要求每个 Attribute payload 重复保存默认 GUID。

# 八、重开后 `FindAttribute` 崩溃的真实解释

OCP 自定义包装是：

```cpp
Handle(TDF_Attribute) dummy_attr;
auto rv = self.FindAttribute(anID, dummy_attr);
anAttribute.Restore(dummy_attr);
return rv;
```

这里没有：

```cpp
if (rv && !dummy_attr.IsNull())
```

检查。([GitHub][2])

如果 Python 当前检查的是旧空文档，Attribute 本来就不存在，那么：

```text
FindAttribute → false
dummy_attr → null
仍然执行 Restore(null)
→ ACCESS VIOLATION 或原生异常
```

所以重开后的崩溃并不说明：

* 文件中的 Attribute 被损坏；
* 反序列化生成了非法对象；
* TNaming 内存被破坏。

它更可能只是：

> 对不存在的 Attribute 调用了一个没有 null guard 的坏包装。

# 九、最先应该执行的修正测试

## 方法 A：直接使用返回 Handle 的 `CDF_Application::Retrieve`

这是目前最值得优先尝试的**纯 Python 绕过方法**。

`CDF_Application::Retrieve(folder, name, ...)` 的返回值是：

```cpp
Handle(CDM_Document)
```

不是输出引用。它内部完成与 `Open()` 相同的 native reader 调用，并直接返回真实文档。([GitHub][10])

测试应改成类似：

```python
from pathlib import Path
from OCP.XCAFApp import XCAFApp_Application
from OCP.BinXCAFDrivers import BinXCAFDrivers
from OCP.TCollection import TCollection_ExtendedString
from OCP.TDocStd import TDocStd_Document

path = Path(xbf_path).resolve()

app = XCAFApp_Application.GetApplication_s()
BinXCAFDrivers.DefineFormat_s(app)

# 关键：不要预创建 doc，不要调用 InitDocument
retrieved = app.Retrieve(
    TCollection_ExtendedString(str(path.parent)),
    TCollection_ExtendedString(path.name),
    True,
)

# OCP 若自动保留动态类型，可直接使用 retrieved；
# 否则使用绑定提供的 DownCast。
doc = TDocStd_Document.DownCast(retrieved)

assert not doc.IsNull()
assert str(app.GetRetrieveStatus()) == "PCDM_ReaderStatus.PCDM_RS_OK"

label = doc.Main().FindChild(1, False)
print(label.NbAttributes())
```

不同 OCP 生成版本的默认参数暴露形式可能不同，必要时补齐 `PCDM_ReaderFilter` 和 `Message_ProgressRange` 参数。

这个测试一旦出现：

```text
NbAttributes == 3
Integer == 42
TNaming_NamedShape 存在
```

就能直接证明：

> XBF 持久化一直正常，问题仅在 `Open` 输出 Handle 绑定。

---

## 方法 B：写一个最小返回值式 C++ 适配层

这是生产系统最稳妥的路线：

```cpp
struct OpenResult
{
    PCDM_ReaderStatus status;
    Handle(TDocStd_Document) document;
};

OpenResult OpenXbf(
    const Handle(TDocStd_Application)& app,
    const std::string& path)
{
    Handle(TDocStd_Document) doc;
    const auto status =
        app->Open(TCollection_ExtendedString(path.c_str()), doc);

    return {status, doc};
}
```

pybind 暴露：

```cpp
m.def("open_xbf", [](const Handle(TDocStd_Application)& app,
                     const std::string& path)
{
    Handle(TDocStd_Document) doc;
    auto status =
        app->Open(TCollection_ExtendedString(path.c_str()), doc);

    return py::make_tuple(status, doc);
});
```

Python 端：

```python
status, doc = ocaf_native.open_xbf(app, xbf_path)
```

同样需要：

```cpp
new_xcaf_document() -> Handle(TDocStd_Document)
find_named_shape(label) -> Handle(TNaming_NamedShape)
find_naming(label) -> Handle(TNaming_Naming)
current_shape(label) -> TopoDS_Shape
```

这不是替代 OCAF，而只是把危险的 C++ 输出引用转换为 Python 友好的返回值。

# 十、应该建立的四象限测试

| Writer | Reader | 能定位的问题                  |
| ------ | ------ | ----------------------- |
| C++    | C++    | 验证 OCCT/XBF 原生基线        |
| Python | C++    | 判断 Python 写入是否正确        |
| C++    | Python | 判断 Python Open/读取绑定是否正确 |
| Python | Python | 验证最终产品链                 |

判定逻辑：

```text
C++ → C++ 成功
Python → C++ 成功
C++ → Python 失败
    = Python Reader / Document Handle 绑定问题

C++ → C++ 成功
Python → C++ 失败
    = Python Writer 或文档创建问题

C++ → C++ 都失败
    = OCCT 环境、驱动、格式或资源问题
```

当前报告只做了 Python→Python，而且两端都使用了含输出 Handle 风险的 API，因此还没有完成真正的故障隔离。

# 十一、诊断时应打开 OCCT 原生日志

OCCT 的读取循环会明确输出：

* type ID 未注册；
* Attribute driver 不存在；
* `Paste()` 返回失败；
* 文件格式不识别；
* EOF 或垃圾数据；
* Shape section 错误。

这些告警都存在于 native retrieval driver 中。([GitHub][9])

因此应向 Application 的 Message Messenger 添加 `Message_PrinterOStream`，将 Reader 日志保存下来。

只有实际出现：

```text
warning: type ID not registered
warning: failure reading attribute TDataStd_Integer
```

才有理由调查 driver table 或 XBF payload。

现在报告没有给出这类 native driver 错误，却直接推断 Paste 未调用，证据链是不够的。

# 十二、可以怎样绕过问题并保留真正的 OCAF 原生持久化

推荐优先级：

## 方案 1：`Retrieve()` 返回值绕过

优点：

* 不修改 OCP；
* 不跨 DLL 传递自定义对象；
* 使用原生 BinXCAF；
* 成本最低。

先用它验证 `Integer` 和 `TNaming` 是否实际存在。

## 方案 2：私有 OCP fork，增加返回值式 API

优点：

* Python 使用体验最好；
* 所有 Handle 由同一个 OCP 扩展管理；
* 不存在跨 DLL RTTI 和引用计数风险；
* 仍是完全原生 OCAF。

这是长期推荐方案。

## 方案 3：独立 C++ OCAF sidecar

Python 只传：

* 文件路径；
* revision ID；
* 稳定标签 Tag path；
* 几何操作历史描述。

C++ sidecar 独占：

* `TDocStd_Document`
* `TDF_Label`
* `TNaming_Builder`
* `TNaming_Selector`
* Save/Open/Solve

这也是完全原生 OCAF，只是将 ABI 风险隔离在进程边界。

## 方案 4：升级到 OCP 7.9.3.1.1 后复测

目前 PyPI 已有 7.9.3.1.1，但升级只能作为对照实验，不能代替故障定位。([PyPI][11])

即使新版修复了输出 Handle，仓库中的以下问题仍需单独重构：

* History 捕获后丢弃真实 old/new Shape；
* `Modify` 被错误写成 `Generated`；
* `Delete` 使用最终 result shape；
* Label 全靠 `NewChild()`，没有稳定身份；
* 创建和重开使用不同 DesignRoot；
* Selection 与业务 Attribute 混用 Label。

# 最终判断

新版报告比上一版前进了一大截，但它只修掉了第一层“同一 Session 没有真正 Open”的问题，又漏掉了第二层：

> **Open 虽然在 C++ 内部成功了，但新的 Document Handle 很可能没有回到 Python。**

报告中 `NewDocument` 测试出现的反常结果几乎已经指向这个问题。

因此当前最优路线不是重写 BinMNaming，也不是先认定 XBF 驱动坏了，而是：

```text
先用 CDF_Application::Retrieve 返回真实文档
或增加 open_xbf() 返回值式 C++ 包装
        ↓
重新执行 Integer / TNaming 跨进程测试
        ↓
用 C++↔Python 四象限确认读写边界
        ↓
确认 XBF 正常后，再重构仓库的 History、Writer、Stable Label
```

我的核心判断仍然保持不变：

> **真正的 OCAF 原生持久化拓扑命名极有可能可以在当前 OCCT 7.8.1 上实现。现在最大的阻塞点不是 BinMNaming 持久化驱动，而是 OCP 对 `Handle(TDocStd_Document)&`、`Handle(TDF_Attribute)&` 等输出引用的错误或不安全包装。**
