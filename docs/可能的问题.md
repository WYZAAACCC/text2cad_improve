# 结论先说

**有办法，而且大概率不需要重写 BinMNaming 持久化驱动。**

我重新对照了：

* 指定提交 `482c2088...` 下两份文档；
* 仓库当前的 `document.py`、`models.py`、`writer.py`、`selectors.py`；
* Boolean、Extrude、Revolve、Fillet 的 History 捕获代码；
* OCCT 7.8.1 的 `TDocStd_Application`、`XCAFApp_Application`、`BinXCAFDrivers`、`BinDrivers`、`TNaming_Tool` 源码；
* OCP 关于 `TDF_Label.FindAttribute` 的已知问题及其修补方式。

得到一个非常关键的结论：

> `OCAF_ABI验证与实验发现_v2.0.md` 中记录的实验现象基本可信，但将其归因于“BinMNaming/BinMDataStd 驱动注册链断裂”，这个根因判断大概率是错误的。

真正的问题至少有四层：

1. 实验根本没有真正重新读取 XBF；
2. OCP 的 C++ 输出参数绑定存在严重语义缺陷；
3. 仓库自身的 OCAF document session 实现有根节点和状态检查错误；
4. 更根本地，仓库在捕获 History 时已经把真实 old/new `TopoDS_Shape` 丢掉了。

因此正确路线不是“先手写 BinMNaming 驱动”，而是：

```text
修正跨进程实验
→ 绕开 OCP 输出引用绑定
→ 保存真实拓扑演化句柄
→ 重写 TNaming Writer
→ 稳定 Label
→ 独立进程 Save/Open/Solve
```

# 一、实验报告中最大的误判：`Open` 实际没有打开文件

实验报告明确记录：

```text
Open(XBF) → PCDM_RS_AlreadyRetrieved
```

但后面仍然继续把 `doc2` 当作“从磁盘重新读取的文档”检查，并据此得出：

* `TDataStd_Integer` 丢失；
* `TNaming_NamedShape` 丢失；
* BinMNaming/BinMDataStd 驱动未调用；
* OCP 属性持久化层断裂。

问题是，OCCT 的源码明确显示：

```cpp
status = CanRetrieve(...);

if (status != PCDM_RS_OK)
{
    return status;
}

// 只有状态为 OK 才执行
D = Retrieve(...);
theDoc = D;
```

也就是说，只要返回 `PCDM_RS_AlreadyRetrieved`，`Retrieve()` 根本不会执行，输出文档也不会被赋成磁盘里的文档。([GitHub][1])

为什么会 `AlreadyRetrieved`？

因为 `SaveAs()` 内部会调用：

```cpp
theDoc->Open(this);
```

并在保存成功后把文档标记为已保存。随后同一个 `XCAFApp_Application` 再打开同一路径，`IsInSession()` 会发现该文件已经处于当前应用会话中，于是返回 `AlreadyRetrieved`。([GitHub][1])

因此报告中的实际流程是：

```text
创建 doc1
→ SaveAs，使 doc1 登记进 Application Session
→ 创建一个空白 doc2
→ Open 同一路径
→ 返回 AlreadyRetrieved，未执行 Retrieve
→ 继续检查空白 doc2
→ 得出“用户属性都丢失”
```

这并不能证明 XBF 持久化失败。

---

# 二、为什么“重开后只剩两个 XCAF 属性”反而证明检查的是空文档

报告发现，所谓“重开文档”中只剩：

* `TDataStd_Name`
* `XCAFDoc_ShapeTool`

于是将其解释为“XCAF 自带属性被持久化，用户属性被丢弃”。

但仓库和 OCCT 的行为提供了更简单的解释。

实验创建 `doc2` 后调用：

```python
app.InitDocument(doc2)
```

`XCAFApp_Application::InitDocument()` 的源码会直接在新文档的 `Main()` 上调用：

```cpp
XCAFDoc_DocumentTool::Set(doc->Main());
```

也就是说，**一个刚初始化、尚未从磁盘读取任何数据的空 XCAF 文档，本来就会具有这些基础 XCAF 属性。** ([GitHub][2])

所以观察结果：

```text
只有 TDataStd_Name + XCAFDoc_ShapeTool
```

不是“用户属性被反序列化器删了”的证据，反而高度符合：

> `Open` 没有执行，检查的是刚刚初始化出来的空白 XCAF 文档。

这意味着实验报告中的 P-03A：

> “所有用户添加属性在 XBF 重开后均丢失”

目前并没有被正确实验所证明。

# 三、第二个问题：OCP 的 `FindAttribute` 输出参数绑定确实有坑

报告中的另一个现象是：

```python
ns = TNaming_NamedShape()
has_ns = label.FindAttribute(TNaming_NamedShape.GetID_s(), ns)
# has_ns == True

TNaming_Tool.CurrentShape_s(ns)
# Standard_NullObject: A null Label has no attribute
```

报告据此判断：

> `TNaming_Tool.CurrentShape_s` 在保存前也不可用。

但 OCP 项目早已有公开问题：`TDF_Label.FindAttribute` 的 C++ 签名使用输出 Handle：

```cpp
bool FindAttribute(
    const Standard_GUID& id,
    Handle(TDF_Attribute)& attribute
);
```

原始自动绑定不能正确更新 Python 传入的对象。OCP issue #55 对这一现象有直接记录。([GitHub][3])

OCP 后来的修补方式并不是把真正的 `Handle(TDF_Attribute)` 返回给 Python，而是：

```cpp
Handle(TDF_Attribute) dummy_attr;
auto rv = self.FindAttribute(anID, dummy_attr);
anAttribute.Restore(dummy_attr);
return rv;
```

即：

> 查到真正属性后，调用用户传入的空属性对象的 `Restore()`，把内容复制过去。([GitHub][4])

这并不等价于获得文档中真正的 Attribute Handle。

`Restore()` 的设计用途是事务回滚时复制“属性内容”，不是把一个独立属性对象重新挂接到原来的 `TDF_Label` 上。([Open CASCADE Technology][5])

而 `TNaming_Tool::CurrentShape()` 对 `TNaming_SELECTED` 类型会访问：

```cpp
Att->Label().FindAttribute(...)
```

如果 Python 中的 `ns` 只是一个被 `Restore()` 填充过、但没有归属 Label 的独立对象，那么 `Att->Label()` 就是空 Label，恰好会产生报告中的错误。([GitHub][6])

因此更合理的解释是：

```text
FindAttribute 返回 True
≠
Python 变量 ns 已经成为文档中的真实 TNaming_NamedShape Handle
```

所以 P-02：

> `TNaming_Tool.CurrentShape_s` 本身不可用

同样尚未被证明。

它很可能只是拿到了一个“内容类似，但脱离 Label 的壳对象”。

# 四、BinMNaming 驱动并没有像报告推测的那样需要 Python 手工注册

实验报告推测：

> `BinXCAFDrivers.DefineFormat_s()` 可能只注册 XCAF 框架驱动，没有正确注册 BinMNaming、BinMDataStd 等子驱动。

但 OCCT 7.8.1 源码中的调用链非常明确：

```cpp
BinXCAFDrivers::DefineFormat(app)
    → BinXCAFDrivers_DocumentRetrievalDriver
    → BinXCAFDrivers::AttributeDrivers()
    → BinDrivers::AttributeDrivers()
```

而 `BinDrivers::AttributeDrivers()` 明确调用：

```cpp
BinMDF::AddDrivers(...)
BinMDataStd::AddDrivers(...)
BinMDataXtd::AddDrivers(...)
BinMNaming::AddDrivers(...)
BinMDocStd::AddDrivers(...)
BinMFunction::AddDrivers(...)
```

也就是说，`TDataStd` 与 `TNaming` 的二进制持久化驱动是由 OCCT 原生 C++ 内部注册的。([GitHub][7])

Python 并不需要逐个调用：

* `BinMNaming_NamedShapeDriver.Paste()`；
* `NewEmpty()`；
* `BinMNaming::AddDrivers()`。

这些操作发生在 C++ 的文档持久化驱动内部。

因此我不建议按实验报告中的方案，去编写一个“手动绑定 BinMNaming driver 的 C++ bridge”。那是在修一个目前没有证据表明确实存在的问题。

需要桥接的不是持久化驱动，而是：

> **OCP 对 C++ 输出引用、派生 Attribute Handle 和 Document Handle 的不安全绑定。**

# 五、仓库当前 `document.py` 本身也会制造“重开失败”

指定提交下的 `OcafDocumentSession` 有三个严重问题。

## 1. 完全不检查 `Open` 状态

当前代码：

```python
app.Open(TCollection_ExtendedString(str(path)), doc)
```

调用后没有获取或检查 `PCDM_ReaderStatus`，无论：

* `PCDM_RS_OK`
* `PCDM_RS_AlreadyRetrieved`
* `PCDM_RS_NoDriver`
* `PCDM_RS_OpenError`
* `PCDM_RS_ReaderException`

都会继续返回一个看似正常的 session。([GitHub][8])

这使得“空文档冒充成功重开文档”成为必然风险。

## 2. 创建和重开的 DesignRoot 不一致

创建时：

```python
self._design_label = doc.Main().NewChild()
```

也就是：

```text
DesignRoot = 0:1:1
```

重开时却写成：

```python
session._design_label = doc.Main()
```

即：

```text
DesignRoot = 0:1
```

所以即使文件已经被正确读取，重开后也会从错误根节点寻找 Component、Feature 和 Selection。([GitHub][8])

指导文档实际上已经指出：创建和重开必须通过固定 Tag 恢复同一个 DesignRoot，禁止把 `doc.Main()` 直接当 DesignRoot。([GitHub][9])

## 3. Label 根本不稳定

`get_or_create_component_label()` 名义上是 get-or-create，但实现最后无条件：

```python
return self._design_label.NewChild()
```

这意味着同一个 `component_id` 每次都获得新 Label。([GitHub][8])

`writer.py` 中 Result、Relation 等也全部使用 `NewChild()`。

因此 Revision 1 和 Revision 2 很可能是：

```text
Revision 1:
component_A → 0:1:1:1

Revision 2:
component_A → 0:1:1:9
```

没有稳定 Label，TNaming 再强也救不了它——连“谁是同一个特征”都没定义。

# 六、即使修好 XBF，当前 writer 仍不可能实现正确 TNaming

这是比 ABI 更根本的问题。

## 1. 数据模型主动丢弃了真实 Shape

`EvolutionRelation` 只保存：

* `old_shape_evidence`
* `new_shape_count`
* 字符串角色；
* 几何证据信息。

它明确不保存：

```python
old_shape: TopoDS_Shape
new_shapes: tuple[TopoDS_Shape, ...]
```

([GitHub][10])

但 TNaming 的原生语义需要真实拓扑对象：

```cpp
Generated(oldShape, newShape)
Modify(oldShape, newShape)
Delete(oldShape)
```

OCCT 明确规定：

* Primitive：空 old → new；
* Generated：old generator → new；
* Modify：old → modified new；
* Delete：old → null；
* 一个 split 可以有相同 old 对应多个 new。([Open CASCADE Technology][11])

如果捕获层只留下“面积、质心、数量”，writer 无法事后恢复真正的演化关系。

## 2. History 捕获代码查到了真实 Shape，然后立即扔掉

Boolean 中已经正确调用：

```python
gen_list = history.Generated(fw)
mod_list = history.Modified(fw)
```

但循环变量 `_gen_shape` 没有写进 `EvolutionRelation`，只保存了数量和 evidence。([GitHub][12])

Extrude、Revolve、Fillet 也一样：

```python
gen_list = builder.Generated(...)
mod_list = builder.Modified(...)
```

查到了真实结果，却只记录：

```python
new_shape_count = gen_list.Size()
```

([GitHub][13])

这是当前 OCAF 路线最大的实质性断点。

## 3. writer 目前写入的演化语义是错误的

当前实现中：

```python
DELETED:
    b.Delete(batch.result_shape)

GENERATED:
    b.Generated(batch.result_shape)

MODIFIED:
    b.Generated(batch.result_shape)
```

也就是说：

* 删除某个旧面，被写成“删除最终实体”；
* 某面生成多个新面，被写成“最终实体是 Primitive”；
* Modify 被写成 Generated；
* old shape 完全不存在。

([GitHub][14])

这不是“不够精准”，而是 TNaming 语义完全错误。

# 七、真正可行的解决方案

我建议采用下面的组合方案。

## 方案核心：原生 OCAF + 安全 OCP 适配层

```text
Python / Text-to-CAD
        ↓
安全 OCP Adapter
        ↓
OCCT 原生 TDocStd / TNaming
        ↓
BinXCAF 原生 XBF 持久化
```

这里的 Adapter 只负责：

* 返回真正的 `Handle(TDocStd_Document)`；
* 返回真正的 `Handle(TNaming_NamedShape)`；
* 返回真正的 `Handle(TNaming_Naming)`；
* 在 C++ 内调用 `CurrentShape`；
* 避免 Python 输出参数和 `Restore()` 假 Handle。

它**不替代 OCAF，不自定义拓扑数据库，也不手写二进制序列化**，所以仍然是真正的 OCAF 原生持久化拓扑命名。

# 八、第一步：重新做一套不会测错对象的 ABI 测试

必须废弃“同一个进程里 Save 后再 Open 同一路径”的测试。

正确 T0 应拆成两个独立进程。

## Writer 进程

```text
进程 A
1. GetApplication
2. BinXCAFDrivers.DefineFormat
3. NewDocument("BinXCAF")
4. 固定 Tag 创建 Label
5. 写 TDataStd_Integer
6. 写 TNaming_Builder.Generated
7. 独立 Selection Label 调 TNaming_Selector.Select
8. CommitCommand
9. SaveAs
10. 检查 PCDM_SS_OK
11. 进程退出
```

## Reader 进程

```text
进程 B
1. 新 Python 进程
2. GetApplication
3. BinXCAFDrivers.DefineFormat
4. Open 文件
5. 必须断言 PCDM_RS_OK
6. 固定 Tag 找 Label
7. 枚举所有 Attribute
8. 检查 TDataStd_Integer
9. 检查 TNaming_NamedShape
10. 检查 TNaming_Naming
11. 解析 CurrentShape
```

不能接受：

```text
PCDM_RS_AlreadyRetrieved
```

也不能把它当成“重开成功”。

指导文档中提出的 fresh document/subprocess 思路是正确的，只是实验报告没有真正遵守。([GitHub][9])

# 九、必须为 OCP 增加“返回值式 API”

## 为什么不能继续使用当前形式

以下 API 都是 C++ 输出引用：

```cpp
Open(path, Handle(TDocStd_Document)& doc)
NewDocument(format, Handle(TDocStd_Document)& doc)
FindAttribute(guid, Handle(TDF_Attribute)& attr)
TDF_Tool::Label(data, entry, TDF_Label& label)
```

这类 API 正是自动 pybind 包装最容易出问题的地方。

生产代码不应继续使用：

```python
empty_obj = SomeAttribute()
label.FindAttribute(guid, empty_obj)
```

也不应假定：

```python
app.Open(path, precreated_doc)
```

会把 Python 变量可靠地重新绑定到新的 C++ Handle。

## 建议的 C++ 适配 API

最好直接在私有 OCP wheel 中增加：

```cpp
std::pair<PCDM_ReaderStatus, Handle(TDocStd_Document)>
OpenXbf(const std::string& path);

Handle(TDocStd_Document)
NewXcafDocument();

Handle(TNaming_NamedShape)
FindNamedShape(const TDF_Label& label);

Handle(TNaming_Naming)
FindNaming(const TDF_Label& label);

TopoDS_Shape
CurrentShapeAt(const TDF_Label& label);

TDF_Label
LabelFromTags(
    const Handle(TDF_Data)& data,
    const std::vector<int>& tags,
    bool create);
```

关键实现形式应是：

```cpp
Handle(TNaming_NamedShape)
FindNamedShape(const TDF_Label& label)
{
    Handle(TNaming_NamedShape) attr;
    if (!label.FindAttribute(TNaming_NamedShape::GetID(), attr))
    {
        return {};
    }
    return attr;
}
```

这里返回的是文档中的真实 Handle，而不是：

```cpp
defaultObject.Restore(realAttribute)
```

`CurrentShapeAt()` 也应完全在 C++ 中完成：

```cpp
TopoDS_Shape CurrentShapeAt(const TDF_Label& label)
{
    Handle(TNaming_NamedShape) ns;
    if (!label.FindAttribute(TNaming_NamedShape::GetID(), ns))
    {
        return {};
    }

    return TNaming_Tool::CurrentShape(ns);
}
```

## 为什么推荐修改同一个 OCP wheel

Windows 下不建议随便编译一个独立 `.pyd`，再让它与 OCP 对象互传 Handle。若它链接了另一套 OCCT DLL、不同 MSVC CRT 或不同编译选项，可能出现：

* RTTI 不一致；
* `Standard_Type` 不一致；
* Handle 引用计数跨 DLL 错误；
* pybind 类型注册重复；
* 释放对象时崩溃。

最稳妥的优先级是：

1. **私有 fork OCP，在同一扩展中增加安全方法；**
2. 使用与 OCP 完全相同 OCCT DLL 和工具链编译扩展；
3. 无法保证 ABI 时，改用独立 C++ sidecar 进程，不跨进程传递任何 Handle。

# 十、第二条可靠绕过路线：C++ OCAF Sidecar

若不想维护私有 OCP wheel，可以把所有 OCAF 操作放进一个独立 C++ 程序：

```text
ocaf_service.exe
```

Python 通过 JSON、临时 BREP 或本地 IPC 调用：

```json
{
  "operation": "write_revision",
  "xbf_path": "...",
  "relations": [...],
  "selections": [...]
}
```

C++ sidecar 独占：

* `TDocStd_Application`；
* `TDocStd_Document`；
* `TDF_Label`；
* `TNaming_Builder`；
* `TNaming_Selector`；
* XBF Save/Open；
* Solve 和 CurrentShape。

Python 不接触危险的输出 Handle。

这仍是真正的 OCAF 原生方案，因为：

* 唯一主文档是 XBF；
* Attribute 是 `TNaming_NamedShape` / `TNaming_Naming`；
* 持久化由 `BinXCAFDrivers` 完成；
* 演化关系由 `TNaming_Builder` 写入；
* Selector 由 `TNaming_Selector` 求解。

Sidecar 只是隔离 Python ABI，不是另建一套拓扑命名系统。

# 十一、仓库需要怎样改

## 1. 重写 `models.py`

改成明确分离 live 与 audit：

```python
@dataclass(frozen=True)
class LiveEvolutionRelation:
    relation_id: str
    kind: EvolutionKind

    old_shape: TopoDS_Shape | None
    new_shapes: tuple[TopoDS_Shape, ...]

    entity_type: str
    source_role: str
    quality: HistoryQuality
```

另设：

```python
@dataclass(frozen=True)
class EvolutionRelationAudit:
    relation_id: str
    kind: EvolutionKind
    old_shape_evidence: dict | None
    new_shape_evidence: tuple[dict, ...]
```

正确原则：

```text
Live relation → 写 TNaming
Audit relation → JSON、日志、排错
```

绝不能反过来根据 evidence 重新猜 Shape。

指导文档提出的 `LiveEvolutionRelation` 方向是正确的。([GitHub][9])

## 2. 修复 tracked operations

以 Boolean 为例，当前代码应从：

```python
for _gen_shape in gen_list:
    EvolutionRelation(
        old_shape_evidence=...,
        new_shape_count=...
    )
```

改成：

```python
generated = tuple(gen_list)

if generated:
    relations.append(
        LiveEvolutionRelation(
            relation_id=...,
            kind=EvolutionKind.GENERATED,
            old_shape=fw,
            new_shapes=generated,
            entity_type="face",
            source_role=role,
            quality=HistoryQuality.EXACT_KERNEL,

```

Modify：

```python
modified = tuple(history.Modified(fw))

if modified:
    relation = LiveEvolutionRelation(
        kind=EvolutionKind.MODIFIED,
        old_shape=fw,
        new_shapes=modified,
        ...
    )
```

Delete：

```python
if history.IsRemoved(fw):
    relation = LiveEvolutionRelation(
        kind=EvolutionKind.DELETED,
        old_shape=fw,
        new_shapes=(),
        ...
    )
```

Extrude、Revolve、Fillet、Chamfer、Clean 都要按同样原则保存真实 Shape。

Fillet 还应取消“边数组下标是身份”的做法。当前 `edge_idx` 只能作为本次执行时的输入定位，不能作为跨 Revision 身份。([GitHub][15])

## 3. 重写 `writer.py`

严格按 TNaming 语义写入：

```python
if rel.kind == PRIMITIVE:
    assert rel.old_shape is None
    for new_shape in rel.new_shapes:
        builder.Generated(new_shape)

elif rel.kind == GENERATED:
    assert rel.old_shape is not None
    for new_shape in rel.new_shapes:
        builder.Generated(rel.old_shape, new_shape)

elif rel.kind == MODIFIED:
    assert rel.old_shape is not None
    for new_shape in rel.new_shapes:
        builder.Modify(rel.old_shape, new_shape)

elif rel.kind == DELETED:
    assert rel.old_shape is not None
    assert not rel.new_shapes
    builder.Delete(rel.old_shape)
```

OCCT 要求一个 `TNaming_Builder` 使用一种 evolution 类型；一个 old 分裂为多个 new 时，可在同一个 Builder 中记录多个同类 old/new pair。([Open CASCADE Technology][11])

必须删除：

```python
except Exception:
    pass
```

任何 TNaming 写入失败都应成为 revision hard failure。

## 4. 建立稳定 Label 树

建议固定根结构：

```text
0:1                Main
└── 1              DesignRoot
    ├── 1          Schema
    ├── 2          Components
    ├── 3          Selections
    ├── 4          Revisions
    ├── 5          CAEBindings
    └── 6          IDIndex
```

组件和 Feature 不应依赖执行顺序 `NewChild()`，而应有持久映射：

```text
(component, "disk") → tag 17
(feature, "rim_slot_cut") → tag 42
(selection, "bore_surface") → tag 8
```

映射本身要写入 OCAF，例如使用：

* `TDataStd_AsciiString`；
* `TDataStd_Name`；
* 固定整数 Tag；
* 冲突检测。

不要简单使用：

```python
tag = hash(object_id)
```

因为 Python hash 默认跨进程不稳定，而且存在冲突。

---

## 5. 修复 `document.py`

创建与打开必须统一：

```python
DESIGN_ROOT_TAG = 1

# create
design_root = doc.Main().FindChild(DESIGN_ROOT_TAG, True)

# reopen
design_root = doc.Main().FindChild(DESIGN_ROOT_TAG, False)
if design_root.IsNull():
    raise OcafSchemaError(...)
```

打开必须：

```python
status, doc = ocaf_native.open_xbf(path)

if status != PCDM_RS_OK:
    raise OcafOpenError(status)
```

不能继续使用当前这种忽略返回值的实现。([GitHub][8])

创建新文档最好调用原生 `NewDocument()`。OCCT 的升级说明明确建议新 OCAF 文档通过 Application 的 `NewDocument()` 创建，XDE 官方示例同样使用 `NewDocument("BinXCAF", doc)`。([GitHub][16])

但由于 `NewDocument` 也有输出 Handle 参数，Python 侧仍建议通过安全适配函数返回 Document Handle。

# 十二、Selector 的正确使用方式

## Selection Label 必须独占

`TNaming_Selector.Select()` 会重建所在 Label 的命名属性，因此 Selection Label 不应同时保存业务属性。

推荐结构：

```text
SelectionObject
├── Metadata
│   ├── selection_id
│   ├── policy
│   └── semantic_contract
└── NativeNaming
    ├── TNaming_NamedShape
    └── TNaming_Naming
```

## Revision 1

```python
selector = TNaming_Selector(native_label)
ok = selector.Select(selected_shape, context_shape)
```

## Revision 2

先写入所有真实：

* Generated；
* Modify；
* Delete；

再调用：

```cpp
selector.Solve(valid_labels)
```

并通过 C++ 安全辅助函数获取 current shape。

## 不能自动最近邻兜底

结果必须区分：

```text
UNIQUE
SET
DELETED
AMBIGUOUS
UNRESOLVED
SEMANTIC_MISMATCH
```

几何指纹可以用来：

* 显示候选；
* 迁移旧模型；
* 人工修复；
* 诊断 TNaming 失败。

不能作为“原生拓扑身份”的权威来源。

# 十三、保存必须改成真正的事务和原子发布

正确 Revision 生命周期：

```text
Open 上一有效 XBF
→ NewCommand
→ 更新几何
→ 写真实 TNaming history
→ Solve 所有 required selections
→ 语义后验检查
→ CAE binding preflight
→ CommitCommand
→ SaveAs(temp.xbf)
→ 独立子进程 Open temp.xbf
→ 验证所有关键 Attribute 和 Selection
→ os.replace(temp.xbf, official.xbf)
```

当前 `document.py` 虽然有 `fsync`，但没有完成“临时文件—重开验证—原子替换”的完整闭环；而且 `_fsync_*` 中仍存在静默异常。([GitHub][8])

指导文档对这个流程的设计基本正确。([GitHub][9])

# 十四、必须建立四象限实验，才能真正定位剩余问题

仅测试 Python 写、Python 读，不足以区分：

* OCCT 持久化问题；
* OCP 写绑定问题；
* OCP 读绑定问题；
* Application Session 问题。

需要四组：

| Writer | Reader | 用途               |
| ------ | ------ | ---------------- |
| C++    | C++    | 验证 OCCT/XBF 基线   |
| Python | C++    | 验证 Python 写入是否正确 |
| C++    | Python | 验证 Python 读取绑定   |
| Python | Python | 最终产品链路           |

判断方式：

```text
C++→C++ 失败
    → OCCT、驱动、格式或环境问题

C++→C++ 成功，Python→C++ 失败
    → Python 写入调用/事务/Handle 问题

C++→C++ 成功，C++→Python 失败
    → OCP 读取和输出参数绑定问题

前三个成功，Python→Python 失败
    → Python Session、生命周期或包装代码问题
```

此外，每个 Reader 都必须记录：

```text
ReaderStatus
IsInSession(path)
Document path
Main Tag tree
每个 Label 的 Attribute 动态类型
TNaming evolution
NamedShape 是否拥有非空 Label
CurrentShape 类型与数量
```

# 十五、是否需要升级 OCP

可以测试升级，但不应把它当成唯一解。

当前已有更新的 `cadquery-ocp` 7.9.3 系列包，但升级会同时改变：

* OCCT 几何行为；
* CadQuery 兼容性；
* Boolean 和 Fillet History；
* STEP 行为；
* ABI；
* 现有测试基线。

([PyPI][17])

推荐顺序是：

1. 在 7.8.1.1 上先修正实验；
2. 用 C++ 四象限证明 XBF 本身是否正常；
3. 增加返回值式安全绑定；
4. 再用同一套 T0～T12 测 7.9.x；
5. 只有完整几何回归和拓扑回归通过后才升级。

单纯升级不会修复仓库中：

* 丢弃 old/new Shape；
* writer 写错 evolution；
* Label 不稳定；
* DesignRoot 错位；
* FEA 使用指纹或索引；

这些应用层问题。

# 十六、我建议的最终实施路线

## 第一阶段：纠正诊断

删除或修订实验报告中的以下结论：

* “BinMNaming 子驱动没有注册”；
* “所有用户 Attribute 均不能持久化”；
* “TNaming_Tool.CurrentShape 本身不可用”；
* “必须手写 BinMNaming 序列化驱动”。

替换为：

> 当前实验受到 `PCDM_RS_AlreadyRetrieved` 和 OCP 输出 Handle 绑定缺陷污染，尚未完成有效的跨进程 XBF 读取验证。

## 第二阶段：安全绑定

new_xcaf_document()
open_xbf()
find_named_shape()
find_naming()
current_shape_at()
label_from_tags()
solve_selection()
```

全部返回真实对象或值，不使用 Python 输出参数。

依次修改：

ocaf/document.py

```

## 第四阶段：原生验收

至少通过：

* T2：三进程 Rev1→Rev2→Solve；

* T10：Selection semantic contract；
* T11：XBF 临时文件损坏不覆盖上一版本；
* T12：CAE required binding 全部可解析。

指导书中已有相近测试矩阵，可以保留并加入 C++/Python 四象限。([GitHub][9])

# 最终判断

**真正的 OCAF 原生持久化拓扑命名是可以实现的。**

目前最合理的技术判断是：

1. OCCT 7.8.1 的 BinXCAF/BinMNaming 原生持久化链没有被现有实验有效证伪；
2. 实验报告中的“属性全部丢失”很可能是检查了一个没有真正加载 XBF 的空文档；
3. `FindAttribute` 与其他输出引用在 OCP 中确实不安全，需要返回值式 C++ 适配；
4. 不需要重写 BinMNaming driver；
5. 需要重写的是仓库自身的 History 数据模型、TNaming Writer、稳定 Label 和 Revision 生命周期；
6. 私有 OCP 安全绑定或独立 C++ sidecar 都可以绕过 Python ABI，同时保持 XBF、TNaming 和 Selector 完全原生。

一句话概括：

> **当前不是“OCAF 做不到”，而是实验没有真正 Open、Python 没拿到真正 Handle、应用层又没有保存真正的 old/new Shape。把这三层分开修，原生跨进程 Select→Save→Open→Modify→Solve 的闭环是有明确实现路径的。**
