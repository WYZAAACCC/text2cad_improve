闭环的八个断点

一个 agent 驱动的涡轮盘设计闭环，九轮真实验，每一轮都停下来了—— 而停下来的地方从来不是物理。生成、划网格、ANSYS 求解这些环节一次没坏； 坏的全是 agent 阶段，以及两轮之间的接缝。

01

这个闭环在做什么

输入是一份涡轮盘的设计参数，输出是下一版的改法。四个接口，全部是可替换的函数， 所以整条链可以在没有 CAD 内核、没有求解器、没有模型的情况下被测。

关键的设计决定是：一条 finding 不是结论，是一个可检验的论证。它必须同时携带五样东西：

  • 机制——从封闭词表里选（局部集中 / 整段过载 / 环向驱动 / 径向驱动 / 载荷施加 / 理想化边界 / 无法归因），因为词表是 harness 能检验的东西
  • 证据——每一个数都要写它是在哪里读的（node:246 / face:14 / field:max_von_mises_mpa），harness 逐条重读
  • 改动——生成侧自己的参数名，加上改成多少
  • 预测——指标、方向、幅度，写成下一轮可以证伪的形式
  • 理由——一段散文

harness 重读每一个数、把机制和它自己的特征做比对、检查改动够不够得着目标， 然后把每一条的残差报回去。它不拒绝——做工程判断的是 agent，harness 不知道什么是对的。 它做的是让这个论证可被检验，这和选面阶段用 criterion 检查 agent 的声明是同一件事。

02

八个断点

九轮真实验，每一轮都停下来了。按发生的位置分类，正好八类——而且它们全部落在 agent 阶段或两轮之间的接缝上：

生成、划网格、ANSYS 求解这些环节，没有一次是因为物理本身而失败的。 唯一一次求解失败是负主元（刚度矩阵非正定），发生在一个网格比上一轮细 1.6 倍的 revision 上—— 那是网格与约束的问题，不是设计的问题。

①契约

反馈 agent · 提交时的模型校验

agent 提交的改动写成 {"variable":..., "current":..., "proposed":...}， 而我的模型要求 {"parameter":..., "current_value":..., "proposed_value":...}。 ProposedChange(**change) 展开时抛异常，炸掉了一次已经跑完的求解—— 选面、两套网格、ANSYS，半小时起，为一个字段名作废。

ValidationError: 5 validation errors for ProposedChange — parameter Field required / variable Extra inputs forbidden / …
已修　提示词里写出准确的键名与完整 JSON 形状； 提交时校验并给 agent 一次改正机会；识别常见同义词（variable→parameter）， 无法识别的键丢弃并记录，不致命。

②能力

反馈 agent · 工具集

四轮里同一件事以四种面貌出现，每次都以为是最后一个： 它有正确的诊断，但够不到。

  • 峰值关联不到 CAD 面 → 补 locate_point（包围盒预筛 + 内核精确点面距离）
  • 变量名不在它被告知的词汇表里 → 那个词汇表本身是错的（见 ⑤）
  • 看到了参数，但不知道它在哪 → 补 at_r_mm
  • 看到了顶点，但不知道它管哪条边 → 补 spans_r_mm
  • 161 个可改量里没扫到对的那个 → 补 near_r_mm（按半径问"什么能改这里"，161 → 21）
"No editable parameter acts at r=208: the slot-cutter fillets are all at r=277.9-284.3, and the disc polyline vertices spanning 160-240 reshape the web/rim section, not the fir-tree flank"

而峰值其实在一个减重孔的边缘上——名字里没有任何东西说"r=208"。

③重复

反馈 agent · 被调用了两次

反馈阶段既注册在链路的末端，又被循环的 diagnose 调一次。 第二次的产出覆盖了第一次，修改 agent 拿到的是一份这一轮从没做过的诊断， 代价是两轮模型调用。

④诚实

修改 agent · 声称与事实

提交 applied: ["F1"]，而没有任何东西被写过—— 没有设参数，没有改脚本。循环信了它，拿完全相同的设计去生成下一版。

校验当时只查了 id 是不是已知 finding，没查这个 id 背后有没有改动。 一个声称被执行、背后却什么都没有的 finding，和一个没被读到的 finding，在记录里长得一样。

已修　每次改动记录它是为哪条 finding 做的； 声称被应用的 finding 必须有一条改动对应，否则拒绝。

⑤层

反馈 ↔ 修改 · 词汇表

我把生成侧的可改面编码成了 param_templates.build() 的入参字典—— 而循环驱动的其实是 CAD 文档。param_templates 只是产出文档的一道工序。

文档里有 31 个操作，每个有自己的参数；榫齿刀上就有 7 个 fillet_sketch， 每个带一个 radius_mm——那些半径在模板的入参字典里一个都没有。

"root_fillet_mm is real in the authoring vocabulary and this generator has no control for it"　← 这句话是错的，而它读起来像是查过了
已修　设计本体改为 document.json； 提示词改掉"这些名字是生成器接受的，没有别的"那句；删掉 not_in_template 这条校验—— 它把"我的词汇表里没有"报成了"生成器做不到"。

⑥恢复

反馈 agent · provider 层

模型吐出的工具调用参数不是合法 JSON（第 2139 字符处一个字符不对）。 schema 不匹配能被转成一次可重试的工具回复，但解析失败发生在更早的地方，直接掀掉了整个 run—— 801 秒的生成、184,337 节点的网格、一次完整求解，全部作废。

LlmToolCallError: Tool call arguments were not valid JSON: Expecting ':' delimiter: line 1 column 2139 (char 2138)
已修　同一个错误早发生一步，就走同一条路： 记进 rejected_calls，回一条"这次调用读不了，什么都没跑，再发一次—— 太长了就发短点"，然后继续。

⑦传递

两轮之间 · 四个决定

这一类比前六类都隐蔽，因为它不报错，只是让对比变得不可解读。 上一轮的分析决定没有传到下一轮：

03

测量纪律：信号必须大于噪声

前六类修完，链路能跑通了——然后发现对比根本读不出来。同一份设计（rim_mm=30， 20 孔 @ pcd 208，60 槽），三份不同的网格：

运行网格节点max von Mises (MPa)
live239,4441875.82
live3282,2621764.98
live7240,0511709.37

散布 9.74%。而且注意 live 与 live7——网格规模几乎相同（239,444 对 240,051）， 峰值仍差 9.74%。所以这个噪声不是单元数量的函数，而是节点落在集中区哪个位置的问题。

由此得到的判据

任何小于约 10% 的"设计效果"，都读不出来。前面八轮里那些 −1.72%、−0.00% 的对比，全部落在噪声里—— 它们说明不了任何事，无论方向看起来多对。

与此相关的还有三件被算了却没人读的东西：

  • 收敛研究跑了，结果没人用。划网格阶段在两级分辨率上各解一次， 两个 structural_metrics.json 就躺在磁盘上；而 verify.py 找的是 convergence_report.json——没有任何代码会写那个文件。所以每一个 真跑过收敛研究的 run，都被告诉"没做过研究"。实测：峰值在 181,362 与 194,011 节点之间动了 5.09%。
  • sel 是一列死数据。deck 写的是 ANSYS 的 NSEL 掩码 （*VGET,MSK(1),NODE,1,NSEL），而在那个位置没有任何东西收窄过选择—— 实测 257,401 行全是 1。而 postprocess_structural.py 拿它当过滤条件用。
  • 应力分量被算出来又扔掉了。deck 写 s_radial, s_hoop, s_axial, s_eqv 四列， _read_csv 四个都解析进 row dict，然后只留 s_eqv。 而诊断恰恰活在被扔的那两个数里——孔边 s_hoop=1482 而 s_radial=0.8； 榫齿 s_radial=1188 而 s_hoop=268。 同一个盘、两个机理、两个相反的改法，而报告里只有后者看不见。

峰值精确地跟到了被改的那个顶点上：

rev-1（原孔）246208.08718.1121709.4

物理上说得通，而且事先就说得出。把一个顶点从局部半径 6 推到 7， 相邻两点仍在 6——轮廓在那里形成一个尖角，而尖角就是新的应力集中源。

内部一致性也对：受载面在榫齿 r = 280–295，与孔不相干。受载面峰值那 +2.93% 里，+2.52% 来自压力变化（选中面积 2679.2 → 2611.2 mm²， 同一个合力），几何只贡献 +0.40%。说明那个 +45.65% 确实来自被改的顶点， 不是某个全局效应串了进来。

这一轮证明了什么、没证明什么

证明了回路能正确地检验一个假设。定位、改动、可比求解、预测检验， 四步都对，而且拿到了 +45.65% 这个远超噪声底的数字。

没证明它能优化应力。这一轮改动让应力变差了 46%。 但它现在手里有一条实测信息：在这个位置加尖角 → 峰值 +46%。 下一步该做的是反过来——把那一组顶点做圆滑过渡，而不是推出尖角。

05

可改面的三层

「生成侧能改什么」有三层，而把第三层当成全部，正是断点 ⑤：

层是什么数量例子
模板参数param_templates.build() 的入参 18 od_mm、bore_mm、rim_mm、depth_mm
文档标量文档 31 个操作各自 params 里的每个数 161 n_fillet_cutter_0.radius_mm、n_pat_holes.radius_mm
轮廓顶点每个 profile 的每个顶点坐标 含在上面 feat_holes_poly.points[4].y_mm

每一层都带着它的位置：

feat_holes_poly.points[12].x_mm  = -0.0   at_r_mm=208.087  spans_r_mm=[205.779, 210.369]
n_pat_holes.radius_mm            =  208   at_r_mm=208.0
n_fillet_cutter_0.radius_mm      =  0.85  at_r_mm=284.309
n_disc_polyline.points[3].y_mm   = -15.0  at_r_mm=240.0    spans_r_mm=[160.0, 240.0]

at_r_mm 是它自己在哪；spans_r_mm 是它能够到哪。 对一个顶点，决定射程的是后者——移动一个顶点会转动与它相邻的两条边， 所以它能重塑的是两个邻点半径之间的整段。峰值在 208，而 n_disc_polyline.points[3] 在 240、跨 160–240，所以它是够得着的。

局部坐标到世界坐标的变换只有一条规则，而且是验证过而不是假设的：

world_r = pattern_radius_mm + 局部x_mm

验证方式：把 n_fillet_cutter_0 从 0.698 改到 1.05——只改这一个参数—— 实际移动了 1,064 个面，面心半径从 283.7 到 295.4 mm；而它的六个顶点在 x = −5.760 / −10.892 / −15.721，按公式给出 r = 294.24 / 289.11 / 284.28。三个都在那组里。

06

还没解决的

最要紧的一条：孔的切割链上没有任何圆角操作。

特征切割链圆角数
榫齿槽 cutters ← extrude ← fillet_6 ← … ← fillet_0 7
减重孔 holes ← extrude ← close ← add_polyline 0

孔是光秃秃的 16 边形直接拉伸切出来的——每个孔 16 个尖角，20 个孔共 320 个， 而那个 +45.65% 的峰值就落在其中一个上（points[12] 的世界半径 208.087）。

所以正确的下一步——「给孔加倒圆」——需要的不是改一个数，而是往文档里加一个操作。 而回路现在只能改值（标量、顶点），不能改结构。这是它的能力边界，也是这个案例真正指向的地方。

其余

  • 回路还没做对过一次改动。唯一一次指对位置的结果是 refuted。 用它学到的反过来做——把孔的那组顶点做圆滑过渡而不是推出尖角——才是第一次 "基于上一轮结果做出更好的选择"。
  • 噪声底约 10%，而这是硬约束。同一设计三份网格散布 9.74%，其中两份网格规模几乎相同 （239,444 对 240,051）仍差 9.74%——所以它不是单元数量的函数，是节点落在集中区哪个位置的问题。 小于 10% 的改动永远读不出来，除非两轮共用同一份网格。
  • 知识库还是空的。refuted 那条目前只在临时脚本里算过， 没落盘到 knowledge.json。跑一次正式的 score_applied 才能写进去。
  • 四个接口从来没一起跑过。446 个测试全绿，但它们跑在假函数上； 真正把 generate/solve/diagnose/revise 全部接上连跑两轮的，只有那九轮手工驱动。
  • 接触参照还没做。整个项目最初的那个未验证前提依然成立： 常应力分片试验只说明一条载荷施加路径更自洽，没说明它符合真实。
